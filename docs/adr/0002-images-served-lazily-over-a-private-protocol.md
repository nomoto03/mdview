# 画像は独自プロトコルで遅延配信し、鮮度よりも軽さを取る

WebViewのベースURLはVite成果物を指すため、Markdown内のローカル画像はディスク上の実体に
到達する手段がなく、常に壊れた画像になっていた。これを塞ぐにあたり、`mdimg` スキームを
Rust側に登録し、HTML生成時に `<img src>` をドキュメントのディレクトリ基準で解決した
絶対パスへ書き換え、WebViewから要求された時点で初めてファイルを読んで返すことにした。

**base64のdata: URIに埋め込む案を退けたのは、初期表示の速さを守るため。** data: URIは
全画像をエンコードし終えるまで本文が1文字も表示されず、`loading="lazy"` も原理的に効かず、
内容の更新のたびに全画像を再転送する。独自プロトコルなら、画像のないドキュメントの
処理経路は現状と完全に同一のままで、画像は本文表示後に遅延して埋まる。

**画像はキャッシュさせ、更新の追跡はしない。** URLにmtimeを混ぜる案も、画像自体を監視対象に
加える案も検討したが、いずれも「内容を保存するたびに参照中の全画像をstatする」コストを
常時払うことになる。画像を描き直しながら見る用途はウィンドウを開き直せば足りると判断した。
監視対象はドキュメント1つのままである。

## Consequences

- 読み取り範囲をドキュメントの配下に限定しない。`../assets/` に共有画像を置く構成が普通で
  あるうえ、CSPが `default-src 'self'` である以上、読んだ画像を外部へ送り出す経路がない
  （インラインスクリプトもインラインイベントハンドラも遮断済み）。mdviewはそもそも
  任意のファイルを開くビューアであり、画面に映すこと自体は権限の拡大にあたらない。
- **UNCパス (`\server\share\x.png`) だけは拒否する。** これはWindows固有で、画像の読み込みが
  そのままSMB接続になり、ユーザーのNTLMハッシュが外部サーバへ渡る実在の漏洩経路になる。
  読み取り範囲を制限しない方針の、唯一の例外。
